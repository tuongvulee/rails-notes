Nền tảng MVC & convention over configuration

Đọc hiểu cấu trúc một Rails app, viết được CRUD cơ bản, nắm routing và validation.

1.1

MVC cơ bản

Junior

Rails theo mô hình MVC: Model (dữ liệu & business logic, ánh xạ bảng DB qua ActiveRecord), View (giao diện, file .erb), Controller (nhận request, gọi Model, chọn View để render). Triết lý cốt lõi là "convention over configuration" — đặt tên file/class đúng quy ước thì Rails tự động kết nối chúng, không cần khai báo thủ công.

# app/models/post.rb
class Post < ApplicationRecord
end

# app/controllers/posts_controller.rb
class PostsController < ApplicationController
  def show
    @post = Post.find(params[:id])   # Model
  end                                # Tự động render app/views/posts/show.html.erb
end
Vì sao Rails tự tìm được view

Vì tên controller PostsController, action show khớp quy ước với thư mục app/views/posts/show.html.erb — không cần khai báo render tường minh nếu đúng convention.

Nhưng MVC chỉ là ba mảnh cốt lõi. Một Rails app thật có thêm nhiều thành phần khác nằm ngoài MVC, mỗi thành phần một thư mục riêng dưới app/. Biết bản đồ này sớm giúp bạn không nhét mọi thứ vào Model/Controller (fat model, fat controller) khi mới bắt đầu.

Lưu ý

Các thư mục đánh dấu * (services, serializers, policies) không phải convention gốc của Rails — không tự sinh ra khi chạy rails new. Đây là quy ước do cộng đồng/team tự thêm, và vẫn được autoload bình thường miễn nằm trong app/ (nhờ Zeitwerk — xem mục 4.1). Ngược lại, models, views, controllers, jobs, mailers, channels có sẵn ngay từ đầu.

Vì sao † lại nằm trong lib/, không phải app/

Middleware object được khởi tạo đúng 1 lần lúc boot rồi bọc cứng vào chuỗi Rack app — khác với Controller/Model được resolve lại mỗi request, nên cơ chế reload code của Zeitwerk không áp dụng đúng cho middleware nếu đặt trong app/. Từ Rails 7.1, config.autoload_lib mặc định autoload luôn lib/ (trừ assets, tasks), nên lib/middleware/ giờ có thể autoload được như các thư mục khác. Tuy vậy, vì middleware được tham chiếu ngay lúc boot (trong config/application.rb), nhiều team vẫn require_relative tường minh cho chắc chắn — xem ví dụ ở mục 3.10.

Nếu dùng GraphQL hoặc gRPC

Bảng trên áp dụng cho Rails app REST/HTML thông thường. GraphQL và gRPC có cấu trúc thư mục khác đáng kể — xem chi tiết ở mục 4.4.

1.3

Active Record cơ bản

Junior

ActiveRecord là ORM ánh xạ table thành class, row thành object. Migration định nghĩa thay đổi schema theo thời gian, có thể chạy tới/lui (rails db:migrate / rollback).

# db/migrate/20240101120000_create_posts.rb   (tên file bắt đầu bằng timestamp 14 chữ số)
class CreatePosts < ActiveRecord::Migration[8.0]
  def change
    create_table :posts do |t|
      t.string :title
      t.text :body
      t.timestamps
    end
  end
end

post = Post.create(title: "Hello", body: "Nội dung")
Post.find(post.id)
Post.where(title: "Hello").first
post.update(title: "Xin chào")
post.destroy

change chỉ hoạt động khi Rails tự suy luận ngược được thao tác đó lúc rollback. Khi thao tác không đối xứng (làm và hoàn tác không phải phép toán ngược của nhau), phải dùng up/down.

Tình huốngTạo bảng, thêm cột, thêm index, đổi tên cột — các thao tác cấu trúc thông thường

Dùng change — Rails biết chính xác cách đảo ngược (create_table ↔ drop_table, add_column ↔ remove_column...)

Tình huốngXoá một cột bằng remove_column

Vẫn dùng change, nhưng phải khai rõ kiểu dữ liệu của cột — nếu không, Rails không biết tái tạo lại cột gì khi rollback

Tình huốngData migration: backfill, sửa hoặc xoá dữ liệu có sẵn trong bảng

Dùng up/down — dữ liệu đã mất thì không "đảo ngược" được, down thường phải raise ActiveRecord::IrreversibleMigration

Tình huốngchange_column đổi kiểu dữ liệu có khả năng mất thông tin (vd text → integer)

Dùng up/down — Rails không biết cách convert ngược lại một cách an toàn

Tình huốngCần chạy raw SQL tuỳ ý (execute), ví dụ thêm constraint

Dùng up/down, hoặc vẫn giữ change kèm reversible nếu muốn khai cả 2 chiều trong cùng 1 method

# remove_column trong change PHẢI khai type để rollback được
class RemoveLegacyFlagFromUsers < ActiveRecord::Migration[8.0]
  def change
    remove_column :users, :legacy_flag, :boolean, default: false
    # Thiếu :boolean, default: false -> rollback sẽ lỗi ActiveRecord::IrreversibleMigration
  end
end

# up/down — data migration không thể hoàn tác chính xác
class BackfillOrderStatus < ActiveRecord::Migration[8.0]
  class MigrationOrder < ActiveRecord::Base   # model tối giản riêng cho migration, không phụ thuộc code app
    self.table_name = "orders"
  end

  def up
    MigrationOrder.where(status: nil).update_all(status: "pending")
  end
  def down
    raise ActiveRecord::IrreversibleMigration   # backfill xong thì không biết dữ liệu gốc là gì
  end
end

# reversible — vẫn dùng change được cho SQL tuỳ ý, chỉ cần tự khai cả 2 chiều
class AddPositiveAmountCheck < ActiveRecord::Migration[8.0]
  def change
    reversible do |dir|
      dir.up   { execute "ALTER TABLE orders ADD CONSTRAINT positive_amount CHECK (amount > 0)" }
      dir.down { execute "ALTER TABLE orders DROP CONSTRAINT positive_amount" }
    end
  end
end

# Nhiều thao tác đã có helper reversible sẵn, không cần viết SQL thô:
add_check_constraint :orders, "amount > 0", name: "positive_amount"      # đảo ngược được trong change (Rails 6.1+)
Nguyên tắc chọn nhanh

Luôn thử change trước — ít code hơn và Rails tự lo rollback. Chỉ chuyển sang up/down khi Rails báo ActiveRecord::IrreversibleMigration, hoặc khi biết trước thao tác liên quan đến dữ liệu/SQL tuỳ ý không có chiều ngược rõ ràng.

1.4

Controller & Action

Junior

Mỗi action là một method trong controller. params chứa dữ liệu từ request (URL, form, query string). render/redirect_to quyết định response trả về.

class PostsController < ApplicationController
  def create
    @post = Post.new(post_params)
    if @post.save
      redirect_to @post, notice: "Tạo bài viết thành công"
    else
      render :new, status: :unprocessable_content
    end
  end

  private
  def post_params = params.require(:post).permit(:title, :body)   # Rails 8: params.expect(post: [:title, :body]), xem mục 2.3
end
Mã 422

Khi validation thất bại, response phải có status 422 để Turbo hiển thị lại form kèm lỗi. Từ Rack 3.2, tên symbol cũ :unprocessable_entity bị đánh dấu deprecated và được đổi thành :unprocessable_content (cùng là mã 422). Tài liệu này dùng tên mới; nếu app còn chạy Rack cũ hơn 3.1, có thể viết thẳng số status: 422.

Filter (before_action) chạy code trước/sau/quanh action — dùng để gom logic lặp lại như nạp record, kiểm tra đăng nhập. only:/except: giới hạn phạm vi; nếu filter gọi redirect_to hoặc render thì chuỗi bị dừng và action không chạy.

class PostsController < ApplicationController
  before_action :set_post, only: %i[show edit update destroy]
  before_action :require_login              # định nghĩa ở ApplicationController

  private

  def set_post
    @post = Post.find(params[:id])
  end

  def require_login
    redirect_to login_path unless current_user
  end
end
Cạm bẫy cú pháp

Đừng viết method một dòng kèm modifier như def require_login = redirect_to(login_path) unless current_user. Với "endless method", unless ở cuối áp dụng cho cả câu lệnh def chứ không phải thân method: Ruby sẽ đánh giá current_user ngay lúc nạp class và ném NameError. Method có điều kiện thì viết dạng def ... end thông thường, hoặc bọc thân trong ngoặc: def require_login = (redirect_to(login_path) unless current_user).

Lưu ý

after_action chạy sau action, around_action bọc quanh action (vd đo thời gian, đổi Time.zone theo user). Đừng nhét business logic vào filter — filter chỉ nên làm việc "chuẩn bị" cho action, logic phức tạp thuộc về Service Object (mục 2.4).

Form, Flash & Session

Junior

form_with model: post (ở đây post là record truyền vào partial) tự chọn URL và HTTP method — POST cho record mới, PATCH cho record đã có — và tự gắn CSRF token. Khi save thất bại, controller render lại form với status: :unprocessable_content (422) để Turbo hiển thị lại trang kèm lỗi.

<%# app/views/posts/_form.html.erb %>
<%= form_with model: post do |f| %>
  <% if post.errors.any? %>
    <ul>
      <% post.errors.full_messages.each do |msg| %>
        <li><%= msg %></li>
      <% end %>
    </ul>
  <% end %>

  <%= f.label :title %>
  <%= f.text_field :title %>
  <%= f.text_area :body %>
  <%= f.submit %>
<% end %>

Flash là thông báo tạm thời: đặt ở một action thì có mặt ở action kế tiếp rồi tự xoá. Vì vậy nó đi cùng redirect_to (redirect làm trình duyệt gửi một request mới). Nếu không redirect mà render ngay trong request hiện tại thì phải dùng flash.now, chỉ tồn tại trong request này.

def create
  @post = Post.new(post_params)
  if @post.save
    redirect_to @post, notice: "Đã lưu"              # flash[:notice]: hiện ở trang đích sau redirect
  else
    flash.now[:alert] = "Không lưu được"             # flash.now: chỉ hiện ở lần render này
    render :new, status: :unprocessable_content
  end
end

Session là dữ liệu gắn với một trình duyệt và tồn tại qua nhiều request (ví dụ id người dùng đang đăng nhập). Mặc định Rails lưu toàn bộ session ngay trong cookie (CookieStore), được mã hoá và ký nên người dùng không đọc hay sửa được nội dung. Khi đăng nhập/đăng xuất, gọi reset_session để bỏ session cũ. Thứ tự quan trọng: phải reset trước rồi mới ghi id user, vì reset_session xoá sạch mọi thứ đang có trong session.

def create                                # đăng nhập
  user = User.authenticate_by(email_address: params[:email_address], password: params[:password])
  if user
    reset_session                         # xoá session cũ TRƯỚC (chống session fixation)
    session[:user_id] = user.id           # rồi mới ghi id của người vừa đăng nhập
    redirect_to root_path
  else
    flash.now[:alert] = "Email hoặc mật khẩu không đúng"
    render :new, status: :unprocessable_content
  end
end

def destroy                               # đăng xuất
  reset_session
  redirect_to login_path
end

# Các request sau: đọc id từ session để biết ai đang đăng nhập
def current_user = @current_user ||= User.find_by(id: session[:user_id])

Cookie tuỳ chỉnh dùng cho dữ liệu nhỏ, không phải session (giao diện sáng/tối, id khách vãng lai). Chọn kiểu tuỳ mức độ nhạy cảm của dữ liệu:

cookies[:locale] = "vi"                       # cookie thường: người dùng đọc và sửa được
cookies.signed[:visitor_id] = "abc123"        # có chữ ký chống sửa, nhưng nội dung vẫn ĐỌC được
cookies.encrypted[:theme] = "dark"            # mã hoá + ký: người dùng không đọc, không sửa được
Điểm hay bị hỏi xoáy

(1) Nhầm lẫn kinh điển: đặt flash[:alert] rồi render trong cùng request — thông báo hiện ngay ở trang này và còn hiện lần nữa ở trang kế tiếp. Dùng flash.now với render, dùng flash/notice:/alert: với redirect_to; nếu cần giữ thông báo thêm một request nữa thì có flash.keep. (2) Cookie bị giới hạn khoảng 4KB nên đừng nhét object lớn vào session — chỉ lưu id rồi tải lại từ DB. (3) Session trong cookie không thể bị thu hồi từ phía server (không thể "đăng xuất thiết bị khác" chỉ bằng cách xoá dữ liệu phía server); muốn vậy phải lưu session ở DB, đúng cách generator authentication của Rails 8 làm (mục 2.9).

Bundler, Gemfile & Môi trường

Junior

Gemfile khai báo gem app cần; Gemfile.lock khoá chính xác phiên bản đã resolve để mọi máy (dev, CI, production) chạy cùng một bộ gem — luôn commit cả hai. bundle install cài gem, bundle exec chạy lệnh trong đúng bộ gem đó. Gem có thể chia group để chỉ nạp ở môi trường cần thiết.

# Gemfile
source "https://rubygems.org"

gem "rails", "~> 8.0.0"      # ~> 8.0.0 = >= 8.0.0 và < 8.1 (chỉ nhận bản vá)
gem "pg"

group :development, :test do
  gem "rspec-rails"
  gem "factory_bot_rails"
end

group :development do
  gem "bullet"                # cảnh báo N+1 khi dev
end

Rails có 3 môi trường mặc định: development, test, production, chọn qua biến RAILS_ENV. Mỗi môi trường có file cấu hình riêng trong config/environments/ (bật/tắt cache, reload code, mức log...), và config/database.yml khai báo DB cho từng môi trường.

Rails.env                  # => "development"
Rails.env.production?      # => false

# Đọc biến môi trường: dùng fetch để lỗi rõ ràng ngay lúc boot nếu thiếu
ENV.fetch("REDIS_URL")                    # thiếu -> KeyError
ENV.fetch("PORT", "3000")                 # có giá trị mặc định
Lưu ý

Không commit file .env hay secret dạng plain text vào git. Với API key, mật khẩu DB... hãy dùng Rails credentials được mã hoá (xem mục 3.9) hoặc biến môi trường do hạ tầng cấp phát lúc deploy.

2.1

Active Record nâng cao

Middle

scope định nghĩa query tái sử dụng. Callback (before_save, after_create) chạy tự động quanh vòng đời object — dùng cẩn thận vì dễ gây side-effect ẩn khó trace. N+1 query là vấn đề hiệu năng kinh điển, giải quyết bằng includes (eager loading).

class Post < ApplicationRecord
  scope :published, -> { where(status: "published") }
  before_save :normalize_title              # từ Rails 7.1, dùng `normalizes :title, with: ->(t) { t.strip }` thay cho callback kiểu này

  private

  def normalize_title
    self.title = title&.strip               # &. vì title có thể nil
  end
end

# N+1: mỗi post lại query riêng author -> N+1 query

Rails cũng có sẵn strict_loading (từ 6.1): Post.strict_loading.first.author ném lỗi (hoặc ghi log, tuỳ config.active_record.action_on_strict_loading_violation) ngay khi có lazy loading association, biến N+1 thành lỗi hiện rõ trong test.

preload, eager_load và includes đều giải quyết N+1 nhưng dùng khác nhau — mỗi cách sinh ra chiến lược SQL khác nhau bên dưới:

Nhiều team production chọn dùng tường minh preload/eager_load thay vì để includes tự quyết. Chi tiết: includes chỉ tự chuyển sang JOIN khi Rails nhận ra điều kiện tham chiếu bảng của association (dạng hash như where(authors: {...})); nếu viết điều kiện bằng chuỗi SQL, như where("authors.verified = true"), phải thêm .references(:authors) hoặc dùng thẳng eager_load, nếu không query sẽ lỗi vì bảng authors không được JOIN.

2.2

Resources, Route tường minh & Scope/Namespace

Middle

Ba công cụ này giải quyết ba vấn đề khác nhau, không thay thế nhau: resources cho tài nguyên RESTful đầy đủ (map tới CRUD của một model), route tường minh (get/post/put/delete ..., to:) cho action không có resource/CRUD đứng sau, và scope/namespace để nhóm nhiều route dưới một path/module/tên dùng chung.

Điểm hay gây nhầm lẫn nhất: namespace chỉ là một cấu hình có sẵn của scope — nó áp cả ba thứ cùng lúc (path prefix, module controller, tên route prefix). Nếu chỉ cần đổi một hoặc hai trong ba thứ đó, dùng scope với đúng tham số cần, đừng dùng namespace rồi lại phải "vá" URL hay tên route cho khớp lại.

# 1) resources — CRUD đầy đủ, action gắn với resource cụ thể qua member/collection
resources :posts, only: [:index, :show] do
  member     { patch :publish }      # PATCH /posts/:id/publish
  collection { get :archived }       # GET  /posts/archived
end

# 2) route tường minh — không có resource/CRUD đứng sau
get  "/health",           to: "health#check"
post "/webhooks/stripe",  to: "webhooks#stripe"
get  "/auth/callback",     to: "sessions#create"

# 3a) scope module: — đổi CONTROLLER lookup, giữ nguyên URL và tên route
scope module: "admin" do
  resources :posts    # controller: Admin::PostsController, nhưng URL vẫn là /posts
end

# 3b) scope "(:locale)" — đổi PATH dùng chung, giữ nguyên module và tên route
scope "(:locale)", locale: /vi|en/, defaults: { locale: "vi" } do
  resources :posts    # /posts (mặc định vi), /en/posts ... route name vẫn là posts_path
end                   # locale: /vi|en/ giới hạn giá trị hợp lệ, tránh "/bat-ky-gi/posts" bị khớp nhầm

# 4) namespace — viết tắt khi cần cả path + module + as cùng lúc
namespace :admin do
  resources :posts    # URL: /admin/posts · controller: Admin::PostsController · tên: admin_posts_path
end
Điểm hay bị hỏi xoáy

Dùng nhầm namespace :admin khi thực ra chỉ muốn tổ chức controller vào module Admin:: mà URL vẫn phải là /posts (không phải /admin/posts) là lỗi rất phổ biến — trường hợp đó phải dùng scope module: "admin", không phải namespace.

Ngoài ra, nested resources thể hiện quan hệ cha-con thật sự trong URL, và concern trong routes giúp tái sử dụng một cụm route (như commentable) giữa nhiều resource khác nhau mà không lặp code.

Rails.application.routes.draw do
  concern :commentable do
    resources :comments
  end
  resources :posts,  concerns: :commentable
  resources :photos, concerns: :commentable
end
# => /posts/:post_id/comments, /photos/:photo_id/comments
Khi nào dùng shallow: true

Khi nested resources sâu quá 1 cấp (vd posts/:post_id/comments/:id/replies), dùng shallow: true để URL cho show/edit/update/destroy không cần lặp lại post_id — chỉ route index/new/create mới cần path đầy đủ của cha.

class CheckoutOrder
  def initialize(order) = @order = order

  def call
    return false unless @order.valid?

    PaymentGateway.charge!(@order, idempotency_key: "order-#{@order.id}")

Đừng bọc lời gọi ra dịch vụ bên ngoài (thanh toán, gửi HTTP) bên trong ActiveRecord::Base.transaction: transaction giữ một kết nối DB suốt thời gian chờ mạng, và nếu thanh toán thành công nhưng commit thất bại thì bạn đã thu tiền mà DB không ghi nhận. Thứ tự an toàn là gọi bên ngoài trước với idempotency key, rồi mới ghi kết quả vào DB (xem thêm mục 3.1 và 4.12). Transaction chỉ nên dùng khi cần nhiều thao tác ghi DB nguyên tử với nhau.

2.5

Background Jobs

Middle

ActiveJob là abstraction chuẩn của Rails cho job nền, có thể cắm nhiều adapter (Sidekiq, Resque, Solid Queue). Sidekiq (dùng Redis) là adapter phổ biến nhất trong production trước Rails 8; từ Rails 8, Solid Queue (chạy trên chính database) là mặc định (xem mục 3.13).

class WelcomeEmailJob < ApplicationJob
  queue_as :default
  def perform(user_id)
    UserMailer.welcome(User.find(user_id)).deliver_now
  end
end

WelcomeEmailJob.perform_later(user.id)   # Chạy nền, không block request

Job nền sẽ thất bại và bị chạy lại — do mạng, do deploy giữa chừng, do worker chết. Vì vậy phải thiết kế job idempotent (chạy 2 lần cho kết quả như chạy 1 lần) và khai báo rõ chiến lược retry. Về tham số: ActiveJob chuyển record Active Record thành GlobalID (chỉ lưu "Order#5", không lưu cả object) và nạp lại từ DB khi job chạy, nên perform_later(order) vẫn an toàn và luôn thấy dữ liệu mới nhất; nếu record đã bị xoá trước đó thì job ném ActiveJob::DeserializationError. Truyền id như dưới đây cũng được, và bắt buộc với worker Sidekiq thuần (không qua ActiveJob) vì tham số chỉ được là kiểu JSON đơn giản. Điều cần tránh là nhét dữ liệu "chụp ảnh" (hash lớn, trạng thái cũ) vào tham số.

class ChargeOrderJob < ApplicationJob
  queue_as :critical
  retry_on Net::OpenTimeout, wait: :polynomially_longer, attempts: 5   # lỗi tạm thời -> thử lại, giãn dần
  discard_on ActiveRecord::RecordNotFound                              # order đã bị xoá -> bỏ, retry vô ích

  def perform(order_id)
    order = Order.find(order_id)
    return if order.paid?                          # idempotent: đã xử lý rồi thì bỏ qua
    PaymentGateway.charge!(order, idempotency_key: "order-#{order.id}")
    order.update!(status: :paid)
  end
end
Điểm hay bị hỏi xoáy

Đừng gọi perform_later ngay bên trong transaction chưa commit: job có thể chạy trước khi record được lưu và find thất bại. Hãy enqueue sau khi transaction commit (dùng after_commit, hoặc bật enqueue_after_transaction_commit do Rails 7.2 bổ sung để hoãn enqueue tới khi transaction commit). Trong ví dụ trên, idempotency_key gửi cho cổng thanh toán giúp tránh trừ tiền hai lần khi job retry — xem thêm mục 4.12.

Chọn đúng lỗi để discard_on

Job ở trên nhận order_id (số nguyên) và tự Order.find, nên khi order đã bị xoá lỗi ném ra là ActiveRecord::RecordNotFound — discard_on ActiveJob::DeserializationError sẽ không bắt được lỗi này (đã chạy thử: job vẫn ném RecordNotFound). DeserializationError chỉ xuất hiện khi truyền thẳng record vào job (perform(order), Rails tự tuần tự hoá bằng GlobalID) rồi record bị xoá trước khi job chạy; khi đó dùng discard_on ActiveJob::DeserializationError. Cả hai cách đều đã chạy thử và bỏ job êm. Với retry_on ..., attempts: 5, 4 lần lỗi đầu job được xếp lại, lần thứ 5 lỗi mới được ném ra ngoài.

2.9

Authentication & Authorization

Middle

Hai khái niệm hay bị nhầm: authentication trả lời "bạn là ai?" (đăng nhập), còn authorization trả lời "bạn được làm gì?" (phân quyền). Rails cung cấp sẵn các mảnh cốt lõi cho authentication; authorization thì Rails không có sẵn, thường dùng thêm gem như Pundit hoặc CanCanCan.

Các mảnh dựng sẵn của Rails: has_secure_password (băm mật khẩu bằng bcrypt vào cột password_digest), authenticate_by (kiểm tra đăng nhập, chống timing attack và user enumeration), generates_token_for (token dùng một lần, tự hết hạn — dùng cho reset mật khẩu, xác nhận email).

class User < ApplicationRecord
  has_secure_password                      # cần cột password_digest + gem bcrypt
  normalizes :email_address, with: ->(e) { e.strip.downcase }

  generates_token_for :password_reset, expires_in: 15.minutes do
    password_salt&.last(10)                # đổi mật khẩu -> token cũ tự vô hiệu
  end
end

User.authenticate_by(email_address: "a@b.com", password: "secret")   # => User hoặc nil
token = user.generate_token_for(:password_reset)
User.find_by_token_for(:password_reset, token)                       # => User hoặc nil

Từ Rails 8.0, lệnh bin/rails generate authentication sinh sẵn một hệ thống đăng nhập bằng session có reset mật khẩu: model User, Session (lưu thiết bị/IP), Current; concern Authentication; SessionsController, PasswordsController và mailer đặt lại mật khẩu. Mặc định mọi action đều yêu cầu đăng nhập, action công khai phải khai báo tường minh.

class SessionsController < ApplicationController
  allow_unauthenticated_access only: %i[new create]      # mặc định mọi action yêu cầu đăng nhập

Middle

Enum ánh xạ một cột (thường là integer) sang tập giá trị có tên, tự sinh predicate, bang method và scope. Đây là cách chuẩn để mô hình hoá trạng thái.

end

Post.published             # scope tự sinh

Điểm hay bị hỏi xoáy

Enum lưu số trong DB — không đổi số của giá trị đã có và không chèn giữa danh sách, vì sẽ làm sai toàn bộ dữ liệu cũ. Thêm giá trị mới ở cuối. Enum cũng không thay thế được state machine: nếu cần quy tắc chuyển trạng thái (draft → published được, archived → draft không được), hãy tự kiểm soát hoặc dùng gem như aasm.

STI (Single Table Inheritance) lưu nhiều lớp con trong một bảng, phân biệt bằng cột type. Hợp khi các lớp con gần như dùng chung cột và chỉ khác hành vi.

Callback và transaction: after_save chạy bên trong transaction, trước khi commit. Nếu lúc đó bạn gửi email hoặc enqueue job, job có thể chạy trước khi dữ liệu được commit, hoặc transaction rollback sau đó mà email đã gửi đi. Việc có tác dụng phụ ra ngoài DB phải chạy trong after_commit.

Pagination, Batch & Bulk

Middle

Ba cách tránh nạp quá nhiều dữ liệu cùng lúc: phân trang cho giao diện người dùng, batch cho xử lý toàn bộ bảng, bulk cho ghi nhiều dòng trong một câu SQL.

Tình huốngHiển thị danh sách cho người dùng, vài chục nghìn dòng

Dùng offset pagination (Kaminari, Pagy) — đơn giản, có số trang, nhảy trang tuỳ ý

Tình huốngBảng hàng triệu dòng, infinite scroll hoặc API dùng cursor

# app/services/import_products.rb
require "csv"

class ImportProducts
  Result = Struct.new(:created, :updated, :errors, keyword_init: true)   # errors: [[số dòng, thông báo], ...]

  def initialize(path) = @path = path

  def call
    result = Result.new(created: 0, updated: 0, errors: [])
    CSV.foreach(@path, headers: true, encoding: "bom|utf-8", col_sep: detect_separator)
       .with_index(2) do |row, line|                        # dòng 1 là tiêu đề nên dữ liệu bắt đầu từ dòng 2
      product = Product.find_or_initialize_by(sku: row["sku"].to_s.strip)   # cùng SKU -> cập nhật, không nhân đôi
      was_new = product.new_record?
      product.assign_attributes(name: row["name"], price: row["price"])

      if product.save
        was_new ? result.created += 1 : result.updated += 1
      else
        result.errors << [line, product.errors.full_messages.to_sentence]
      end
    end
    result
  end

  private

  # Excel bản tiếng Việt thường xuất CSV với dấu ";" thay vì ","
  def detect_separator
    first = File.open(@path, "r:bom|utf-8", &:readline)
    first.count(";") > first.count(",") ? ";" : ","
  end
end
class ImportsController < ApplicationController
  MAX_SIZE = 5.megabytes

  def create

    unless File.extname(file.original_filename).casecmp?(".csv") && file.size <= MAX_SIZE

# lib/csv_safe.rb
module CsvSafe
  DANGEROUS_PREFIXES = ["=", "+", "-", "@", "\t", "\r"].freeze

  # Excel coi ô bắt đầu bằng = + - @ là CÔNG THỨC và sẽ thực thi khi người dùng mở file
  def self.sanitize(value)
    return value unless value.is_a?(String)        # số âm (Numeric) không bị ảnh hưởng
    value.start_with?(*DANGEROUS_PREFIXES) ? "'#{value}" : value
  end
end

class ProductsController < ApplicationController
  def index
    respond_to do |format|
      format.html { @products = Product.page(params[:page]) }
      format.csv do
        csv = CSV.generate do |out|
          out << %w[sku name price]
          Product.find_each { |p| out << [p.sku, CsvSafe.sanitize(p.name), p.price] }
        end
        send_data "﻿#{csv}", filename: "products-#{Date.current}.csv", type: "text/csv; charset=utf-8"
      end
    end
  end
end

(1) CSV injection: người dùng nhập tên sản phẩm =HYPERLINK("http://evil..."), sau đó quản trị viên export và mở bằng Excel — công thức chạy trên máy quản trị. Luôn sanitize khi export, không chỉ khi import. (2) Encoding: Excel lưu CSV theo code page hệ thống, nên tiếng Việt dễ hỏng; đọc bằng "bom|utf-8" để bỏ BOM ở đầu file, nếu không tên cột đầu tiên sẽ là "﻿sku" và row["sku"] trả nil. (3) Ngày và số theo locale: 03/04/2026 là 3 tháng 4 hay 4 tháng 3? Parse tường minh bằng Date.strptime(s, "%d/%m/%Y"), không dùng Date.parse. Số kiểu Việt 1.234,56 phải chuẩn hoá trước khi ép sang BigDecimal. (4) Mã có số 0 đứng đầu (số điện thoại, mã bưu chính) phải giữ dạng chuỗi — Excel hay tự ép về số và làm mất số 0. (5) Đừng dùng CSV.parse(file.read) — nạp cả file vào RAM; hãy dùng CSV.foreach đọc từng dòng.

3.1

AR internals: Arel & Locking

Senior

Arel là SQL AST builder nằm bên dưới query interface của ActiveRecord. Optimistic locking dùng cột lock_version để phát hiện xung đột ghi đồng thời; pessimistic locking dùng SELECT ... FOR UPDATE qua with_lock để khoá row khi cần chắc chắn tuyệt đối.

account.with_lock do          # SELECT ... FOR UPDATE — khoá row trong transaction
  account.balance -= amount
  account.save!
end
# Optimistic locking: chỉ cần thêm đúng 1 cột, Rails tự nhận diện và dùng
add_column :posts, :lock_version, :integer, default: 0

post = Post.find(1)
post.update!(title: "Tiêu đề mới")
# => raise ActiveRecord::StaleObjectError nếu ai đó đã sửa post này
#    Kể từ lúc post được load, không cần SELECT ... FOR UPDATE nào cả

Hai chiến lược này dựa trên giả định hoàn toàn khác nhau về xung đột — chọn sai sẽ hoặc gây lost update, hoặc gây nghẽn hệ thống không cần thiết.

Tình huốngForm chỉnh sửa có "thời gian nghĩ" dài giữa lúc đọc và lúc lưu (user mở form edit, gõ 5-10 phút mới submit)

Dùng optimistic — không thể giữ khoá DB suốt thời gian đó, sẽ chặn hết người khác

# Migration: chỉ cần thêm đúng 1 cột, Rails tự nhận diện và dùng optimistic locking
add_column :posts, :lock_version, :integer, default: 0

class PostsController < ApplicationController
  def update
    @post = Post.find(params[:id])
    @post.update!(post_params.merge(lock_version: params[:lock_version]))
    redirect_to @post, notice: "Đã lưu"
  rescue ActiveRecord::StaleObjectError
    # Ai đó đã sửa post này trong lúc user đang gõ form
    flash.now[:alert] = "Bài viết đã bị thay đổi bởi người khác, vui lòng tải lại và sửa lại"
    render :edit, status: :conflict
  end
end
Lưu ý

Form edit phải render kèm field ẩn <%= hidden_field_tag :lock_version, @post.lock_version %> — đây là giá trị Rails dùng để so sánh "phiên bản lúc user mở form" với "phiên bản hiện tại trong DB" khi submit.

Dùng pessimistic — phải chặn tuyệt đối "lost update", sai 1 đồng cũng không chấp nhận được

class InsufficientFunds < StandardError; end

def transfer_money(from_id, to_id, amount)
  ActiveRecord::Base.transaction do
    # Khoá CẢ HAI tài khoản trong một câu lệnh, theo thứ tự id cố định
    accounts = Account.where(id: [from_id, to_id]).order(:id).lock.index_by(&:id)   # SELECT ... ORDER BY id FOR UPDATE
    from, to = accounts.values_at(from_id, to_id)

    raise InsufficientFunds if from.balance < amount      # kiểm tra số dư SAU khi đã khoá
    from.update!(balance: from.balance - amount)
    to.update!(balance: to.balance + amount)
  end
end
Điểm hay bị hỏi xoáy

Deadlock do thứ tự khoá: nếu code khoá tài khoản "gửi" trước rồi mới khoá tài khoản "nhận", hai giao dịch A→B và B→A chạy cùng lúc sẽ mỗi bên giữ một khoá và chờ khoá còn lại — deadlock, database phải huỷ một giao dịch. Cách chuẩn là luôn khoá nhiều dòng theo một thứ tự cố định (ở đây ORDER BY id) bất kể chiều chuyển tiền. Ngoài ra kiểm tra số dư phải nằm sau khi khoá, nếu kiểm tra trước thì hai giao dịch cùng thấy đủ tiền rồi cùng trừ.

Tình huốngĐặt chỗ/mua hàng số lượng giới hạn

Dùng pessimistic — ngăn bán vượt tồn kho khi nhiều request cùng lúc đọc/trừ số lượng còn lại

Tình huốngBackground job xử lý lâu trên 1 record

Dùng optimistic + retry — pessimistic giữ lock lâu sẽ nghẽn cả hệ thống, mọi request khác chờ khoá đó bị treo theo

Hiệu năng & Indexing

Senior

Thêm index cho cột thường dùng trong WHERE/JOIN/ORDER BY. Dùng EXPLAIN ANALYZE để đọc query plan thật sự thay vì đoán.

# db/migrate/..._add_index_to_posts.rb
add_index :posts, :author_id
add_index :posts, [:status, :created_at]   # Composite index cho query kết hợp

puts Post.where(status: "published").order(created_at: :desc).explain(:analyze)   # EXPLAIN ANALYZE: chạy query thật và đo thời gian (Rails 7.1+)
# .explain (không tham số) chỉ là EXPLAIN: ước lượng của planner, chưa chạy query

# Bảng lớn trên PostgreSQL: tạo index không khoá ghi bảng
class AddIndexToPostsStatus < ActiveRecord::Migration[8.0]
  disable_ddl_transaction!                                  # CONCURRENTLY không chạy được trong transaction
  def change
    add_index :posts, [:status, :created_at], algorithm: :concurrently
  end
end
Đã đo trên PostgreSQL 18 (bảng 1 triệu dòng, có luồng UPDATE chạy song song)

add_index thường chặn ghi trong suốt thời gian tạo index; add_index ... algorithm: :concurrently không chặn (lệnh ghi chậm nhất 13ms trong khi tạo index). Migration dùng :concurrently bắt buộc phải có disable_ddl_transaction! — trong transaction, PostgreSQL từ chối lệnh.

Chạy trên MySQL

algorithm: :concurrently và disable_ddl_transaction! là của PostgreSQL. Trên MySQL 8.4, add_index ... algorithm: :concurrently báo ArgumentError (chỉ nhận :default, :copy, :inplace, :instant). Đã đo trên bảng 1 triệu dòng có luồng ghi chạy song song: add_index mặc định và algorithm: :inplace đều không chặn ghi (lệnh ghi chậm nhất khoảng 40ms trong 5 giây tạo index), còn algorithm: :copy chặn ghi 40 giây — tránh. Tham số lock: :none không có trong add_index; muốn chỉ định cứng thì dùng SQL thô execute "ALTER TABLE posts ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE" (cũng đã đo: không chặn ghi).

Điểm hay bị hỏi xoáy

Index không miễn phí — mỗi INSERT/UPDATE/DELETE phải cập nhật tất cả index của bảng đó, và mỗi index tốn thêm dung lượng đĩa. Đừng index mọi cột "phòng khi cần" — chỉ index cột thực sự xuất hiện trong WHERE/JOIN/ORDER BY của query thật, và dùng EXPLAIN ANALYZE để xác nhận index có được dùng hay không (Index Scan vs Seq Scan) thay vì đoán.

3.5

Security: CSRF, XSS, SQLi

Senior

Rails có sẵn CSRF token bảo vệ form, tự động escape output trong ERB chống XSS, và ActiveRecord dùng parameterized query chống SQL injection — miễn là tránh raw SQL interpolation thủ công.

# NGUY HIỂM — SQL injection qua interpolation trực tiếp
Post.where("title = '#{params[:title]}'")

# AN TOÀN — dùng placeholder, Rails tự escape
Post.where("title = ?", params[:title])
Post.where(title: params[:title])

XSS có một cửa hậu quen thuộc: ERB chỉ tự escape chuỗi thường, còn chuỗi đã đánh dấu "an toàn" thì in nguyên văn. Đây là lỗi XSS phổ biến nhất trong app Rails:

<%= @post.body %>                 # AN TOÀN: tự escape, "<script>" hiện thành chữ
<%= raw @post.body %>             # NGUY HIỂM: in nguyên HTML người dùng nhập
<%= @post.body.html_safe %>       # NGUY HIỂM: tương tự, nói với Rails "tin chuỗi này"
<%= sanitize @post.body %>        # Cho phép một số thẻ HTML lành tính, loại bỏ phần nguy hiểm
<%= link_to "Web", @post.url %>   # Coi chừng url dạng "javascript:..." nếu url do người dùng nhập
Điểm hay bị hỏi xoáy

Chạy brakeman (static analysis security scanner) định kỳ trong CI để bắt các pattern nguy hiểm này trước khi merge. Chỉ dùng raw/html_safe với nội dung chính bạn sinh ra, không bao giờ với dữ liệu do người dùng nhập. Thêm một lớp phòng thủ bằng Content Security Policy (config/initializers/content_security_policy.rb) để trình duyệt từ chối chạy script không nằm trong danh sách cho phép, kể cả khi lọt XSS.

3.6

Multi-tenancy

Senior

Ba cách phổ biến: cột tenant_id trong mọi bảng (row-level, đơn giản nhất, dễ triển khai nhất), schema riêng mỗi tenant (Postgres schema, cô lập hơn), database riêng mỗi tenant (cô lập tuyệt đối, phức tạp nhất khi vận hành/migrate).

# app/models/concerns/tenant_scoped.rb — gắn vào TỪNG model có cột tenant_id
module TenantScoped
  extend ActiveSupport::Concern

  included do
    belongs_to :tenant
    default_scope { where(tenant_id: Current.tenant&.id) }   # row-level multi-tenancy
    before_validation { self.tenant ||= Current.tenant }     # bản ghi mới tự gắn tenant hiện tại
  end
end

class Invoice < ApplicationRecord
  include TenantScoped
end

Lý do dùng concern gắn từng model thay vì đặt default_scope ở ApplicationRecord: cách sau áp lên mọi model, kể cả Tenant hay các bảng dùng chung không có cột tenant_id, và làm hỏng chúng. default_scope ngắn gọn nhưng là nguồn rò dữ liệu giữa các tenant phổ biến nhất, vì Current.tenant chỉ tồn tại trong phạm vi một request. Ở nơi không có request (background job, console, rake task), nó là nil — query sẽ lọc tenant_id IS NULL hoặc, tệ hơn, nếu ai đó gọi unscoped thì lấy hết dữ liệu mọi tenant.

# app/models/current.rb
class Current < ActiveSupport::CurrentAttributes
  attribute :tenant
end

# Request: xác định tenant ngay đầu request (vd theo subdomain)
class ApplicationController < ActionController::Base
  before_action { Current.tenant = Tenant.find_by!(subdomain: request.subdomain) }
end

# Job: PHẢI truyền tenant_id và tự set lại, vì Current không đi theo job
class ReportJob < ApplicationJob
  def perform(tenant_id)
    Current.set(tenant: Tenant.find(tenant_id)) do
      Report.generate    # trong block này default_scope mới có tenant
    end
  end
end
Điểm hay bị hỏi xoáy

Với multi-tenancy row-level, phòng thủ nhiều lớp: (1) đặt tenant_id NOT NULL và index [:tenant_id, ...] trên mọi bảng, (2) cấm/giới hạn unscoped qua code review, (3) test tự động tạo dữ liệu 2 tenant và khẳng định tenant A không bao giờ thấy dữ liệu của B, (4) với yêu cầu cô lập cao, dùng Postgres Row Level Security để chính database chặn — không chỉ dựa vào tầng ứng dụng. Gem acts_as_tenant đóng gói sẵn nhiều điểm trên.

end

3.10

Rack Middleware, CORS & Rate limiting

Senior

Rails app thực chất là một Rack app: một object có method call(env) trả về [status, headers, body]. Middleware là các lớp bọc quanh app đó, mỗi lớp nhận request đi vào và response đi ra — đây là chỗ Session, cookie, CSRF, log, thu gọn exception đều được xử lý trước khi tới Router. Xem toàn bộ chuỗi bằng bin/rails middleware.

# lib/middleware/request_timer.rb
class RequestTimer
  def initialize(app) = @app = app          # nhận app kế tiếp trong chuỗi

  def call(env)
    started = Process.clock_gettime(Process::CLOCK_MONOTONIC)
    status, headers, body = @app.call(env)  # chuyển request xuống lớp trong, nhận response lên
    ms = ((Process.clock_gettime(Process::CLOCK_MONOTONIC) - started) * 1000).round
    headers["x-runtime-ms"] = ms.to_s       # Rack 3: tên header phải viết thường (Rails đã có sẵn Rack::Runtime, đây chỉ là ví dụ minh hoạ)
    [status, headers, body]
  end
end

# app/models/product_row.rb — kiểm tra một dòng file, không chạm DB
class ProductRow
  include ActiveModel::Model
  attr_accessor :sku, :name, :price
  validates :sku, :name, presence: true
  validates :price, numericality: { greater_than: 0 }
end

class ImportProductsJob < ApplicationJob
  queue_as :imports                        # queue riêng để import lớn không chặn job quan trọng khác
  BATCH_SIZE = 1000
  MAX_ERRORS = 10_000

  def perform(import)                    # GlobalID tự nạp lại record từ DB lúc job chạy
    import.processing!
    errors = []
    processed = 0

    import.file.open do |tempfile|         # tải về file tạm trên đĩa, không đọc cả file vào RAM
      opts = { headers: true, encoding: "bom|utf-8" }
      import.update!(total_rows: CSV.foreach(tempfile.path, **opts).count)   # đếm trước để có % tiến độ

      CSV.foreach(tempfile.path, **opts).each_slice(BATCH_SIZE).with_index do |rows, batch|
        valid = []
        rows.each_with_index do |row, i|
          line  = batch * BATCH_SIZE + i + 2                  # +2: bỏ dòng tiêu đề, đánh số từ 1
          attrs = row.to_h.slice("sku", "name", "price")
          check = ProductRow.new(attrs)
          check.valid? ? valid << attrs : errors << [line, check.errors.full_messages.to_sentence]
        end

        valid = valid.reverse.uniq { |a| a["sku"].to_s.strip }.reverse   # cùng SKU trong 1 lô: giữ dòng CUỐI (xem callout bên dưới)
        Product.upsert_all(valid, unique_by: :index_products_on_sku) if valid.any?   # 1 câu SQL cho cả lô
        processed += rows.size
        import.update!(processed_rows: processed)             # cập nhật tiến độ theo LÔ, không theo từng dòng
        break if errors.size >= MAX_ERRORS                    # file lỗi quá nhiều thì dừng sớm
      end
    end

    attach_error_report(import, errors)
    import.update!(status: :completed, failed_rows: errors.size)
  rescue StandardError
    import&.failed!
    raise                                  # để backend job ghi nhận và retry theo cấu hình
  end

  private

  def attach_error_report(import, errors)
    return if errors.empty?
    csv = CSV.generate do |out|
      out << %w[dong loi]
      errors.each { |line, message| out << [line, CsvSafe.sanitize(message)] }   # message có thể chứa dữ liệu người dùng
    end
    import.error_report.attach(io: StringIO.new(csv), filename: "loi-import-#{import.id}.csv", content_type: "text/csv")
  end
end
Chạy trên MySQL

Trên MySQL, thay dòng upsert_all bằng Product.upsert_all(valid) if valid.any? (bỏ unique_by, vẫn cần unique index trên sku). Đã chạy thử nguyên job trên MySQL 8.4: SKU trùng → dòng cuối thắng, báo cáo lỗi đúng, tiếng Việt (utf8mb4) không hỏng. Bước khử trùng uniq ở trên vẫn nên giữ để hành vi giống nhau giữa các CSDL — riêng MySQL không lỗi nếu bỏ nó, khác với PostgreSQL.

Điểm hay bị hỏi xoáy

Nếu cùng một SKU xuất hiện hai lần trong cùng một lô, PostgreSQL từ chối câu INSERT ... ON CONFLICT DO UPDATE với lỗi "cannot affect row a second time" — cả lô 1000 dòng thất bại chỉ vì một cặp trùng. SQLite chạy êm nên lỗi này không lộ khi test bằng SQLite. Vì thế job lọc trùng trong lô trước khi gọi upsert_all (dòng cuối thắng, giống hành vi "cập nhật theo SKU" của luồng import thường). Trùng giữa các lô khác nhau thì không sao, vì mỗi lô là một câu SQL riêng.

File Excel lớn cần đọc dạng streaming: gem roo cho phép duyệt từng dòng của .xlsx mà không nạp cả sheet vào bộ nhớ:

xlsx = Roo::Excelx.new(tempfile.path)
xlsx.each_row_streaming(offset: 1, pad_cells: true) do |cells|   # offset: 1 bỏ dòng tiêu đề
  sku, name, price = cells.map(&:value)
end

Export lớn cũng đi theo hướng bất đồng bộ: thay vì bắt trình duyệt chờ, job dựng file, đính kèm vào Active Storage rồi gửi email/thông báo kèm link tải. Dùng find_each để bộ nhớ không đổi dù bảng có bao nhiêu dòng, và ghi thẳng ra file tạm thay vì gom thành một chuỗi khổng lồ.

class ExportOrdersJob < ApplicationJob
  queue_as :exports

  def perform(export_id)
    export = Export.find(export_id)

    Tempfile.create(["orders", ".csv"]) do |file|
      csv = CSV.new(file)
      csv << %w[id customer total created_at]
      Order.where(created_at: export.from_date.beginning_of_day..export.to_date.end_of_day)
           .find_each(batch_size: 2000) do |order|                # bộ nhớ không đổi theo kích thước bảng
        csv << [order.id, CsvSafe.sanitize(order.customer_name), order.total, order.created_at.iso8601]
      end
      file.rewind
      export.file.attach(io: file, filename: "orders-#{Date.current}.csv", content_type: "text/csv")
    end

    export.update!(status: :completed)
    ExportMailer.ready(export).deliver_later                      # gửi link tải khi đã sẵn sàng
  end
end
Còn cách stream trực tiếp thì sao?

Có thể stream CSV về trình duyệt ngay trong request (ví dụ với ActionController::Live) để người dùng thấy file tải xuống sớm, nhưng nó giữ một thread Puma và một kết nối DB suốt thời gian tải, proxy/CDN có thể buffer làm mất tác dụng, và khó xử lý khi client ngắt giữa chừng. Với báo cáo lớn hoặc chạy lâu, job nền + link tải là lựa chọn ổn định hơn.

Điểm hay bị hỏi xoáy

(1) Job phải chạy lại được: worker chết hay deploy giữa chừng thì job bị chạy lại từ đầu. Upsert theo khoá tự nhiên (sku) giúp chạy lại không nhân đôi dữ liệu; có thể lưu processed_rows làm checkpoint để bỏ qua các lô đã xong, hoặc dùng Active Job Continuations của Rails 8.1 (mục 3.13). Nguyên lý idempotent xem thêm mục 4.12. (2) Bộ nhớ: dùng CSV.foreach/each_slice, không bao giờ CSV.read cả file, và đặt trần cho danh sách lỗi (MAX_ERRORS) vì file toàn dòng lỗi có thể nuốt hết RAM. (3) Khoá DB: ghi lô lớn vào bảng đang được dùng nhiều có thể gây tranh chấp khoá; giữ transaction ngắn theo từng lô, và cân nhắc chạy vào giờ thấp điểm. (4) Bảo mật: .xlsx thực chất là file zip — giới hạn dung lượng file và số dòng để tránh "zip bomb" giải nén phình to; import vào hệ thống nhiều tenant thì phải truyền tenant vào job (mục 3.6), vì Current không đi theo job. (5) Đặt import/export vào queue riêng và giới hạn số job chạy đồng thời để một file lớn không làm nghẽn các job quan trọng như gửi email hay thanh toán.

4.1

Railtie & Zeitwerk

Principal

Railtie là cơ chế để gem "hook" vào quá trình boot của Rails (thêm initializer, rake task, generator riêng). Từ Rails 6, Zeitwerk thay thế classic autoloader — ánh xạ tên file sang tên class nghiêm ngặt hơn nhưng loại bỏ hàng loạt bug autoload khó hiểu của cơ chế cũ.

class MyGem::Railtie < Rails::Railtie
  initializer "my_gem.configure" do |app|
    app.config.my_gem = MyGem::Config.new
  end
end
Zeitwerk & thứ tự nạp

Khi boot, initializer của framework và của gem (Railtie/Engine) chạy trước, rồi mới tới config/initializers/*.rb của app. Vì vậy trong config/initializers/ có thể dùng cấu hình mà gem đã đăng ký, nhưng không nên tham chiếu trực tiếp class của app (vd User) ở mức top-level: Zeitwerk sẽ nạp class đó ngay lúc boot, và reload trong development sẽ không cập nhật lại. Nếu bắt buộc, bọc trong Rails.application.config.to_prepare { ... }.

Kiểm tra autoload

Tên file phải khớp tên class (app/models/blog_post.rb → BlogPost). Chạy bin/rails zeitwerk:check trong CI để bắt lỗi sớm. Ở production config.eager_load = true nạp toàn bộ class ngay lúc khởi động (nên lỗi tên file lộ ra ngay lúc deploy thay vì lúc chạy), còn development/test dùng nạp lười để boot nhanh.

Toàn cảnh vòng đời một app Rails — từ lúc gõ rails server đến khi xử lý xong một request — gồm 2 giai đoạn tách biệt rõ ràng: khởi động chạy đúng 1 lần, và xử lý request lặp lại vô hạn mà không đụng lại phần khởi động.

Cột trái (xanh) chạy đúng 1 lần khi boot; cột phải (cam) lặp lại cho mỗi request. Đường nối chéo thể hiện: khởi động xong mới "mở khoá" cho việc xử lý request bắt đầu.

4.2

Scaling: Read Replica & Sharding

Principal

Từ Rails 6, hỗ trợ native multiple databases — route query đọc sang read replica giảm tải primary DB qua connects_to. Sharding chia dữ liệu theo khoá (tenant, khu vực) để scale ngang khi một DB không còn đủ.

# config/database.yml
production:
  primary:
    database: myapp_production
    host: primary-db.internal
  primary_replica:
    database: myapp_production
    host: replica-db.internal
    replica: true
class ApplicationRecord < ActiveRecord::Base
  primary_abstract_class   # bắt buộc khi dùng nhiều DB: đánh dấu đây là lớp gốc của kết nối chính
  connects_to database: { writing: :primary, reading: :primary_replica }
end

ActiveRecord::Base.connected_to(role: :reading) do
  Post.count   # Ép query này chạy trên read replica
end
Điểm hay bị hỏi xoáy

Chỉ khai báo connects_to chưa tự động chuyển query đọc sang replica — mặc định mọi query vẫn đi qua role writing. Cần thêm middleware để tự route theo GET/POST:

# config/application.rb
config.active_record.database_selector = { delay: 2.seconds }
config.active_record.database_resolver = ActiveRecord::Middleware::DatabaseSelector::Resolver
config.active_record.database_resolver_context = ActiveRecord::Middleware::DatabaseSelector::Resolver::Session
Lưu ý

Middleware tự nhận diện: GET → đọc từ replica; nhưng nếu vừa có request ghi (POST/PUT/DELETE) trong delay giây gần nhất, nó tạm thời đọc từ primary — vì replica có replication lag, đọc ngay sau khi ghi có thể trả dữ liệu cũ chưa kịp đồng bộ.

Sharding khác replica ở chỗ: replica là bản sao của cùng một dữ liệu (scale đọc), còn shard chứa một phần khác nhau của dữ liệu (scale cả ghi lẫn dung lượng). Rails khai báo nhiều shard trong connects_to shards:, rồi chọn shard cho từng khối code bằng connected_to(shard:).

class ApplicationRecord < ActiveRecord::Base
  primary_abstract_class
  connects_to shards: {
    default:   { writing: :primary,   reading: :primary_replica },
    shard_two: { writing: :shard_two, reading: :shard_two_replica }
  }
end

# Chọn shard thủ công
ActiveRecord::Base.connected_to(shard: :shard_two, role: :writing) do
  Order.create!(customer_id: 42, total: 100)
end

# Hoặc tự chọn shard theo request (vd theo tenant)
# config/application.rb
config.active_record.shard_selector = { lock: true }
config.active_record.shard_resolver = ->(request) { Tenant.find_by!(host: request.host).shard }
Điểm hay bị hỏi xoáy

Sharding có cái giá rất lớn: không JOIN được xuyên shard, transaction không bao được nhiều shard, migration phải chạy lên từng shard, và chọn sai shard key (vd chia theo ngày tạo khiến một shard nóng) thì resharding sau này cực kỳ đau. Chỉ sharding khi đã tối ưu query/index, dùng replica và cache mà vẫn chạm giới hạn ghi hoặc dung lượng của một DB.

Principal

4.4

GraphQL & gRPC

Principal

GraphQL và gRPC là hai kiến trúc API thay thế phổ biến nhất ở quy mô lớn, đi theo hai hướng hoàn toàn khác nhau — mỗi kiến trúc có cấu trúc thư mục và vòng đời request riêng, không giống nhau.

GraphQL

graphql-ruby cho client tự chọn chính xác field cần lấy trong 1 request duy nhất, tránh phải gọi nhiều endpoint hoặc nhận về dữ liệu thừa không dùng đến. Vì mọi request đều đi qua chung một URL, cần gom truy vấn (batching) để tránh N+1 xuyên nhiều resolver — graphql-ruby có sẵn GraphQL::Dataloader cho việc này (không cần gem ngoài) — và caching thường phải làm ở tầng ứng dụng (persisted query, cache theo hash) thay vì dựa vào cache theo URL.

class Types::QueryType < Types::BaseObject
  field :post, Types::PostType, null: true do
    argument :id, ID, required: true
  end
  def post(id:)
    Post.find_by(id: id)   # field null: true → trả nil nếu không có, thay vì ném RecordNotFound
  end
end

Chống N+1 bằng GraphQL::Dataloader (có sẵn trong gem, Rails 8 + graphql-ruby 2.x): khai báo use GraphQL::Dataloader trong schema, viết một source gom nhiều key thành một query, rồi resolver chỉ gọi dataloader.with(...).load(key).

# app/graphql/my_app_schema.rb
class MyAppSchema < GraphQL::Schema
  use GraphQL::Dataloader
end

# app/graphql/sources/record_by_id.rb
class Sources::RecordById < GraphQL::Dataloader::Source
  def initialize(model) = @model = model

  def fetch(ids)                       # nhận TẤT CẢ id đã gom → 1 query duy nhất
    records = @model.where(id: ids).index_by(&:id)
    ids.map { |id| records[id] }       # phải trả đúng thứ tự & số lượng như ids
  end
end

# app/graphql/types/post_type.rb
class Types::PostType < Types::BaseObject
  field :author, Types::UserType, null: true
  def author
    dataloader.with(Sources::RecordById, User).load(object.user_id)   # N post → 1 query users
  end
end

4.5

Observability

Principal

Rails phát instrumentation event nội bộ (sql.active_record, process_action.action_controller) qua ActiveSupport::Notifications — subscribe để đo custom metric mà không cần monkey patch. Các công cụ APM (New Relic, Datadog) build trên chính cơ chế này.

ActiveSupport::Notifications.subscribe("process_action.action_controller") do |event|   # block nhận 1 tham số → Rails tự truyền ActiveSupport::Notifications::Event
  StatsD.timing("request.duration", event.duration)   # duration tính bằng mili-giây
  StatsD.increment("request.status.#{event.payload[:status]}")
end

4.7

Zero-downtime Migration

Principal

Thêm cột NOT NULL trực tiếp trên bảng lớn có thể khoá bảng lâu và chặn ghi — cần chia nhiều bước, mỗi bước một migration/deploy riêng. Gem strong_migrations tự động cảnh báo migration nguy hiểm và gợi ý đúng cách làm. Ví dụ với PostgreSQL:

# Migration 1 — thêm cột nullable (nhanh, không rewrite bảng)
add_column :users, :status, :string
# (deploy code mới: luôn ghi status cho bản ghi mới)

# Migration 2 — backfill theo lô, ngoài transaction để không giữ lock lâu
class BackfillUserStatus < ActiveRecord::Migration[8.0]
  disable_ddl_transaction!

  def up
    User.unscoped.in_batches(of: 10_000) do |batch|
      batch.where(status: nil).update_all(status: "active")
      sleep(0.01)   # nhường DB cho traffic thật
    end
  end

  def down; end
end

# Migration 3 — ép NOT NULL an toàn qua CHECK constraint
add_check_constraint :users, "status IS NOT NULL", name: "users_status_null", validate: false  # chỉ khoá rất ngắn
validate_check_constraint :users, name: "users_status_null"                                      # quét bảng, không chặn ghi

# Migration 4 — PostgreSQL 12+ dùng constraint đã validate để bỏ qua bước quét lại
change_column_null :users, :status, false
remove_check_constraint :users, name: "users_status_null"
Đã đo trên PostgreSQL 18 (bảng 1 triệu dòng, có luồng UPDATE chạy song song)

add_check_constraint ... validate: false chạy tức thì (0,01 giây); validate_check_constraint quét cả bảng nhưng không chặn ghi (lệnh ghi chậm nhất 5ms trong lúc quét); ngược lại, add_check_constraint mặc định (validate: true) chặn ghi trong suốt thời gian quét. Sau khi đã có constraint đã validate, change_column_null :users, :status, false chạy 0,01 giây so với 0,11 giây khi chưa có constraint — PostgreSQL 12+ bỏ qua bước quét lại bảng.

Chạy trên MySQL

Chuỗi CHECK ở trên là của PostgreSQL và không có lợi trên MySQL 8.4 (đã đo, bảng 1 triệu dòng có luồng ghi chạy song song). add_check_constraint ... validate: false bị bỏ qua: Rails vẫn gửi ALTER TABLE ... ADD CONSTRAINT ... CHECK (...) thường, MySQL kiểm tra mọi dòng hiện có (báo CheckViolation nếu còn dòng NULL) và chặn ghi 12,6 giây. validate_check_constraint không tồn tại (NoMethodError). Dùng NOT ENFORCED bằng SQL thô chỉ dời vấn đề: thêm constraint chạy tức thì (0,02 giây) nhưng ALTER TABLE ... ALTER CHECK ... ENFORCED sau đó chặn ghi 15 giây. Cách đúng trên MySQL đơn giản hơn: thêm cột nullable, backfill theo lô, rồi gọi thẳng change_column_null :users, :status, false — đã đo không chặn ghi (5,9 giây, lệnh ghi chậm nhất 205ms; MySQL làm tại chỗ). Lệnh này báo lỗi nếu còn dòng NULL, nên backfill phải xong trước. Cần biết thêm: DDL của MySQL không nằm trong transaction — migration lỗi giữa chừng để lại phần đã làm, không tự rollback (đã thử: cột vẫn còn sau rollback), nên mỗi migration chỉ nên làm một việc. Backfill bằng in_batches và change_column_null(..., false, "active") (chạy UPDATE cả bảng) hành xử y hệt PostgreSQL.

Điểm hay bị hỏi xoáy

change_column_null :users, :status, false, "active" (tham số thứ 4) sẽ chạy UPDATE toàn bảng trong một câu lệnh rồi mới thêm ràng buộc — trên bảng lớn đó là đúng kiểu migration gây sự cố. Chiều ngược lại cũng cần cẩn thận: xoá cột phải làm 2 lần deploy — trước tiên khai báo self.ignored_columns += ["old_col"] trong model và deploy, sau đó mới remove_column, để các process cũ đang chạy không lỗi khi cột biến mất.

Rails Doctrine & Trade-off

Principal

Triết lý "Rails Doctrine" của DHH: convention over configuration, "menu is omakase", "majestic monolith". Ở cấp Principal, hiểu khi nào Rails là lựa chọn đúng (tốc độ phát triển cao, team nhỏ-trung, sản phẩm cần lặp nhanh) và khi nào cần rẽ nhánh sang kiến trúc polyglot/microservice (siêu quy mô, đội ngũ cực lớn, yêu cầu cô lập công nghệ theo domain).

4.9

Principal

Một Engine là "Rails app thu nhỏ" nhúng được vào app khác: có app/, routes, migration, view riêng. Về bản chất Rails::Engine là một Railtie (mục 4.1) có thêm khả năng chứa code ứng dụng. Chính Rails và hệ sinh thái cũng dùng engine: Active Storage, Action Mailbox, Devise đều là engine. Engine phù hợp để đóng gói một tính năng có cả model, controller và view, dùng lại được giữa nhiều app.

4.11

Feature Flags

Principal

Feature flag tách việc deploy code khỏi việc bật tính năng: code mới được đưa lên production ở trạng thái tắt, rồi bật dần cho nhân viên nội bộ, một phần trăm user, rồi tất cả. Nhờ vậy team có thể merge thường xuyên vào nhánh chính (trunk-based), phát hành ít rủi ro, và có "công tắc khẩn cấp" tắt tính năng lỗi trong vài giây mà không cần deploy lại. Gem phổ biến: flipper.

Flipper.enable_percentage_of_actors(:new_checkout, 10)         # bật cho 10% user (ổn định theo từng user)

Flipper.disable(:new_checkout)                                 # kill switch

  render :new_checkout
else
  render :checkout
end
Kết hợp với zero-downtime migration

Feature flag là nửa còn lại của quy trình "expand → migrate → contract" (mục 4.7): thêm cột/bảng mới (expand), viết code đọc/ghi cả hai chỗ sau flag, backfill dữ liệu, chuyển đọc sang chỗ mới bằng cách bật flag từ từ, và chỉ xoá cấu trúc cũ (contract) khi đã chắc chắn.

Điểm hay bị hỏi xoáy

Flag là nợ kỹ thuật có hạn dùng: mỗi flag nhân đôi số đường đi cần test, và flag không ai dọn sẽ tồn tại hàng năm cho tới khi không ai dám gỡ. Đặt người chịu trách nhiệm và ngày xoá cho mỗi flag phát hành (release flag); phân biệt với flag vận hành dài hạn (kill switch, thí nghiệm A/B). Test cả hai nhánh bật/tắt, và đảm bảo rollout theo phần trăm dựa trên id user để cùng một user luôn nhận cùng một trải nghiệm.

4.12

Event-driven, Outbox & Idempotency

Principal

Khi hệ thống có nhiều module hoặc nhiều service, việc "có gì đó xảy ra" thường được phát dưới dạng event (order.paid) để các phần khác phản ứng, thay vì gọi trực tiếp nhau. Vấn đề khó nằm ở dual write: lưu vào DB và gửi event ra broker là hai hệ thống khác nhau, không thể nằm trong cùng một transaction. Gửi trước commit mà transaction rollback thì có event "ma"; gửi sau commit mà process chết giữa chừng thì mất event.

Outbox pattern giải quyết bằng cách ghi event vào một bảng outbox_events trong cùng transaction với dữ liệu nghiệp vụ — hoặc cả hai cùng lưu, hoặc cả hai cùng không. Một tiến trình khác đọc bảng này và publish ra ngoài, lỗi thì thử lại.

ActiveRecord::Base.transaction do
  order.update!(status: :paid)
  OutboxEvent.create!(event_id: SecureRandom.uuid, event_type: "order.paid",
                      payload: { order_id: order.id })         # cùng transaction: nguyên tử
end

class PublishOutboxJob < ApplicationJob            # chạy định kỳ (vd Solid Queue recurring task)
  def perform
    OutboxEvent.where(published_at: nil).order(:id).limit(100).each do |event|
      Broker.publish(event.event_type, event.payload, id: event.event_id)   # có thể bị publish >1 lần
      event.update!(published_at: Time.current)
    end
  end
end

Vì publisher có thể chết sau khi publish nhưng trước khi đánh dấu published_at, event sẽ được gửi ít nhất một lần (at-least-once), có thể trùng. Do đó bên nhận phải idempotent: xử lý cùng một event hai lần cho kết quả như xử lý một lần.

# bảng processed_events có UNIQUE index trên event_id
def handle(event)
  ActiveRecord::Base.transaction do
    ProcessedEvent.create!(event_id: event.id)   # lần 2 sẽ vi phạm unique -> RecordNotUnique
    ShipmentService.create_for(event.payload["order_id"])
  end
rescue ActiveRecord::RecordNotUnique
  Rails.logger.info("Bỏ qua event trùng #{event.id}")
end
Điểm hay bị hỏi xoáy

"Exactly-once delivery" trên mạng thực tế không tồn tại; thứ đạt được là at-least-once + consumer idempotent = xử lý hiệu quả đúng một lần. Nếu chạy nhiều publisher song song, cần cơ chế tránh lấy trùng lô (ví dụ "nhận" lô bằng FOR UPDATE SKIP LOCKED trong một transaction ngắn, hoặc chỉ chạy đúng một publisher) — và đừng giữ transaction mở trong lúc gọi ra broker. Cũng phải tính tới thứ tự: event của cùng một aggregate cần được xử lý theo thứ tự (dùng partition key theo id aggregate), và dọn bảng outbox_events/processed_events định kỳ để không phình vô hạn. Cùng nguyên lý áp dụng cho API công khai: client gửi Idempotency-Key để retry thanh toán không bị trừ tiền hai lần (xem mục 2.5).

Trong một monolith

Nếu chỉ cần các module trong cùng một app phản ứng với nhau (mục 4.3), ActiveSupport::Notifications hoặc job nền là đủ và đơn giản hơn nhiều — chỉ dùng outbox khi event thật sự phải ra khỏi ranh giới process/service và không được phép mất.
